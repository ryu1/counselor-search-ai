# レビュー方針：カウンセラー検索AIデモ

## 1. レビュー観点・チェック項目

### 1.1 正確性 (Correctness)

- [ ] 仕様書（product.md）の要件を満たしているか
- [ ] 検索条件のAND/ORロジックが正しいか（同一項目OR・項目間AND）
- [ ] 日時正規化ロジックが正しいか（相対・絶対・曖昧表現）
- [ ] エッジケース（0件・条件不足・不正入力）が処理されているか
- [ ] SQLがSQLインジェクションに対して安全か

### 1.2 セキュリティ (Security)

- [ ] 入力バリデーションが実装されているか
- [ ] マスター値以外の入力が拒否されるか
- [ ] SQLエスケープが実装されているか
- [ ] DOMPurifyが設定されているか
- [ ] IAMロールが最小権限か
- [ ] 認証情報がソースコードに含まれていないか
- [ ] S3バケットのBlock Public Accessが有効か

### 1.3 パフォーマンス (Performance)

- [ ] Lambda実行時間が300秒以内か
- [ ] Athenaクエリが合理的な時間で完了するか
- [ ] フロントエンドバンドルサイズが200KB以内か
- [ ] 不要なAPI呼び出しがないか

### 1.4 保守性 (Maintainability)

- [ ] 型アノテーションが実装されているか（Python mypy / TypeScript）
- [ ] 関数・クラスが単一責務を守っているか
- [ ] テストが付随しているか
- [ ] 命名規則に従っているか
- [ ] ドキュメントが更新されているか

### 1.5 拡張性 (Extensibility)

- [ ] Tool IFを変更せずにバックエンド差し替えが可能か
- [ ] 新しい検索条件の追加が容易か
- [ ] 将来の認証追加に対応可能か

## 2. PRレビュープロセス

### 2.1 レビュー依頼タイミング

| タイミング | 条件 |
|-----------|------|
| レビュー依頼 | 実装完了・テスト通過後 |
| ワークフロー完了 | CI全ステップ通過後 |
| 再レビュー依頼 | 指摘事項修正後 |

### 2.2 レビュアー指名ルール

| 変更種別 | 必須レビュー数 | 指名ルール |
|---------|--------------|-----------|
| インフラ変更 (CloudFormation) | 1名以上 | チーム内 |
| バックエンド変更 (Lambda) | 1名以上 | チーム内 |
| フロントエンド変更 | 1名以上 | チーム内 |
| セキュリティ関連 | 2名以上 | 全員 |
| ドキュメントのみ | なし | 自己レビュー |

---

## 3. 承認ルール

| 条件 | 値 |
|------|-----|
| 必須承認数 | 1名以上 |
| マージ条件 | CI通過 + 承認済み |
| マージ方法 | スクエッシュマージ |
| ブランチ削除 | マージ後自動削除 |

---

## 4. レビューコメントの粒度・トーン

### 4.1 コメント分類

| マーカー | 意味 | 対応 |
|---------|------|------|
| `[must]` | 修正必須（バグ・セキュリティ） | マージ前に修正 |
| `[should]` | 修正推奨（可読性・保守性） | 対応検討 |
| `[nit]` | 軽微な指摘（命名・フォーマット） | 対応任意 |
| `[question]` | 確認・質問 | 回答記録 |
| `[praise]` | 良い実装の称賛 | 対応不要 |

### 4.2 トーンガイドライン

- 技術的な事実を述べる（「〇〇が可能发生します」）
- 理由を添える（「△△のため、□□が推奨されます」）
- 個人攻撃を避ける（「コードが」而非「あなたが」）
- 提案であれば代替案を示す

## 5. セルフレビュー・チェックリスト

PR作成前に以下を確認:

### コード品質

- [ ] `npm run lint` / `ruff check` が通過
- [ ] `npm run type-check` / `mypy` が通過
- [ ] テストが全通過 (`npm test` / `pytest`)
- [ ] 不要なコメント・console.logがない

### セキュリティ

- [ ] 入力値がバリデーションされている
- [ ] SQLにユーザー入力が直接結合されていない
- [ ] XSS対策（DOMPurify）が機能
- [ ] 認証情報がソースコードにない

### ドキュメント

- [ ] 対応する設計ドキュメントを更新
- [ ] API変更時は api.md を更新
- [ ] データモデル変更時は architecture.md を更新
- [ ] 新規ツール追加時は conventions.md を更新

### テスト

- [ ] 新規機能にテストを追加
- [ ] エッジケースをカバー
- [ ] テストが独立して実行可能
